Austria Key: Complete Reviewer Guide

App name: Австрия Ключ (Austria Key). Operator: TSN «Астрия» (Astria). The app and operator names intentionally differ.

Review candidates: iOS/iPadOS 1.0.0 (11), iOS/iPadOS 17 or later; Android 1.0.0 (3), Android 8.0 or later. Android package: ru.austria.key. iOS bundle: app.bluetoothrelay.ios.

Updated 7 October 2026. Instructions describe these candidates, not earlier test builds. The submitted apps have a Russian interface; this English guide translates the actual control labels. Store approval, tester availability and physical-device verification are separate matters.

Review without hardware is supported for interface, documents and credential import. Demo does not perform Bluetooth access. The public QR/JSON files below are deliberately unregistered import samples: they cannot activate or open a real gate. Actual opening additionally requires a nearby compatible controller and a separately issued operational review credential.

1. Purpose and access model

Austria Key is a free local Bluetooth gate-access utility for users authorized by the operator of the Austria cottage complex. It is not limited to employees. Downloading the app, joining a test track or enabling Demo does not grant physical access. There are no purchases, subscriptions, advertisements, analytics, app login/password or separate app accounts.

  1. An administrator issues a ready-to-import access QR or JSON file for a property and gate. The user does not generate, display or return a request QR from the phone.
  2. The user scans or imports the supplied credential. The app stores it locally and creates a protected phone signing identity.
  3. For the first actual opening, the app exchanges authenticated messages with the nearby controller over Bluetooth. The controller uses its own Wi-Fi/HTTPS connection to bind the issued access to the first phone that successfully activates it.
  4. After activation, subsequent openings use authenticated Bluetooth commands and the controller's synchronized local allowlist. A copied, already activated QR does not authorize a second phone.

The app holds one credential at a time. Import and activation are different steps: a saved credential marked as awaiting activation is not evidence that a controller accepted it. Deleting an activated key or changing phone requires a new credential from the administrator; reinstalling or copying an old QR is not a supported way to transfer access.

3. Hardware-free demo

  1. Open the app. On a fresh installation Settings opens automatically; otherwise use the upper-right menu.
  2. Scroll to «Демонстрационный режим» and switch it on. No login, credential, Bluetooth permission or hardware is required for this step.
  3. Return to the main screen with Done (iOS) or Back (Android). The main screen visibly identifies Demo.
  4. Tap the circular button once. iOS calls it «Проверить демонстрацию»; Android retains «Нажмите, чтобы открыть».
  5. After approximately one second, iOS displays «Демонстрация завершена. Команда калитке не отправлялась.»; Android displays «Демонстрация завершена. Команда не отправлялась». Both explicitly mean that no hardware command was sent.
  6. Return to Settings and inspect the local privacy policy and terms. On iOS also inspect native Help.

Demo disables optional automatic access. It simulates only the visible main-button flow; it does not test Bluetooth discovery, controller authentication, registry activation, a relay pulse, or a physical gate. Android direct-opening widgets intentionally do not issue commands in Demo.

Both display synthetic property 0 and gate austria-review-demo. Their public controller-key value is a standard public test point, not a key belonging to an installed gate. Neither access identifier nor activation proof is registered for real opening.

5. Import test sequence

Use an empty review installation, not an operational user's phone. If Settings shows an unrelated real credential, do not delete or replace it. Use a separate device instead. Before any main-button check after an import, return to Settings and ensure Demo is on. iOS turns Demo off when it accepts a new credential. Android retains the existing Demo setting, so explicitly checking it is still recommended.

A. In-app camera scan

  1. With no saved credential, open Settings and tap «Сканировать QR-код». Allow Camera for this action.
  2. Display Sample A on a different screen, then scan it. Do not scan both samples in the same camera frame.
  3. Expected: the app saves the sample and returns to the main screen. Reopen Settings: property is 0, with an awaiting-first-opening/activation state. Import does not send a gate-opening command.
  4. Enable Demo again before testing the main button. Its expected result remains “command was not sent.”

B. Selected QR image

  1. Delete only Sample A using «Удалить ключ» and confirm. This makes iOS import controls visible again.
  2. Choose «Открыть изображение с QR» on iOS or «Открыть изображение QR-кода» on Android.
  3. Select the locally saved demo-access.png. The system grants access to the selected image, not unrestricted access to the photo library.
  4. Expected: the same Sample A is saved. Reopen Settings, verify property 0 and awaiting activation, then enable Demo before any main-button test.

C. JSON document import

  1. Delete only the currently saved public sample.
  2. Tap «Импортировать файл ключа» and choose the locally saved demo-access.json from Files/the system document picker.
  3. Expected: Sample A is saved without Camera permission. Verify Settings; then restore Demo for hardware-free use.
  4. After finishing Sample A and the guards below, delete only Sample A and import demo-access-file.json. Expected: Sample B is accepted as a different, still non-operational credential.

D. Invalid input and safe cleanup

On an empty review installation, import a small local text/JSON file containing {}, or scan an unrelated QR. Expected: an error and no valid saved access. No command is sent. To finish, remove only the public sample and leave Demo enabled, or leave the app empty. Do not expect the samples to reach Activated status or produce a real controller acknowledgment.

6. Duplicate and replacement guards

Repeat Sample A: once A is saved, deliver the same QR import link again (or use the Android import controls, which remain visible). iOS keeps its existing credential and identity; Android shows «Этот ключ уже добавлен» (“This key is already added”). A duplicate is not a new activation and must not replace an activated receipt with an unactivated copy.

On iOS, camera/photo/file import controls are hidden while a key is saved. To test the saved-key link guard, scan the sample with the normal camera and follow its verified app link. If the OS opens the browser fallback instead, it does not deliver a new credential; that route cannot by itself prove the guard. The ordinary file-import paths can still be tested after removing only the public sample.

Attempt B while A is saved: iOS refuses to replace a different existing key and asks the reviewer to check Settings. Android displays «Заменить ключ?» (“Replace key?”); choose «Отмена» (“Cancel”) to verify that A remains saved. Android intentionally allows a replacement only after explicit confirmation. This is different from the iOS guard and is not an automatic overwrite.

For the normal second-sample test, use Delete key to remove only public Sample A, then import B into the empty app. Never use Replace or Delete on an unrelated operational credential. Deleting local access stops automatic opening; it does not by itself delete the operator's server record.

8. Actual gate opening

Operational review access is separate from these public samples. Any additional credential-supply instructions are provided privately through the store review console. This page does not publish a user's QR, property number, activation code, private key or review-portal password. It does not claim that a portal URL or an operational key has already been delivered. If no operational review access was supplied, contact the developer before attempting the hardware test.

  1. Use a supported physical phone and a nearby compatible controller on a safe test stand. Import the individually issued operational review QR/JSON into an empty app, not one of the public samples.
  2. Leave Demo and optional automatic access off. Enable Bluetooth and allow the required permission.
  3. On Android select «Подключить калитку» in Settings, confirm the supplied controller in the OS chooser and verify «Калитка подключена». The first manual opening can also invoke this association flow.
  4. For first activation, the controller must have working Wi-Fi/server access and a valid trusted clock. The phone does not make this server request. First activation can take longer than later openings.
  5. Return to the main screen and tap the circular button once. It is disabled while the operation is pending; wait for its final status rather than repeatedly tapping.
  6. The app authenticates the controller's challenge and result; the controller validates the phone's proof and assigned access before producing an opening pulse.
  7. On a valid signed confirmation, iOS reports «Команда открытия выполнена контроллером.»; Android reports «Команда открытия подтверждена». The stored access changes to Activated after successful first activation.
  8. Repeat one manual opening to inspect an already activated credential. Do not copy the first QR to another phone and assume it is reusable: the activated access is bound to one phone.

A success status confirms the controller's authenticated software acknowledgment of the opening command/control pulse. The app has no sensor for physical gate position, relay-contact movement, obstacles or a person passing through. A defective relay, wiring or gate mechanism may therefore remain undetected even after a software acknowledgment.

The controller can use its synchronized authorization cache for up to 24 hours after a valid synchronization. First activation requires its server connection; revocation reaches the controller after synchronization. Stale authorization data or an untrusted clock after reboot fails closed. A phone without internet may still open an already authorized nearby gate, subject to these controller conditions.

9. Optional background modes

iOS: Automatic opening nearby

First verify a real manual opening. In Settings switch on «Автоматическое открытие рядом», then allow the app to move into the background and approach the assigned controller. iOS background Bluetooth events may allow a brief authenticated opening attempt when proximity conditions are met. It is an opt-in automatic-access feature; leave it off on an unsafe test stand.

Turning on the iPhone screen is not an API that guarantees app execution or gate opening. Bluetooth scheduling, radio conditions, battery policy and forced termination affect behavior. After force-quitting, reopen the app before expecting background access. Disabling the option or deleting the key stops this app's automatic-access behavior. There is no iOS widget in build 11 and no claim that a background push keeps this app alive.

Android: Open the lock when the screen turns on

  1. Verify ordinary opening using an activated operational credential and the system-associated controller. Leave Demo off.
  2. Enable «Открытие замка по включению экрана». Complete association/Nearby devices permission if prompted; allow Notifications on Android 13+.
  3. Expected persistent service status: title «Австрия Ключ», text «Открытие по включению экрана включено». This indicates the service is enabled, not that a gate is currently open.
  4. Move the app to the background, turn the screen off, wait, then turn it on near the associated test controller. The service attempts authenticated access only when its checks allow it. It checks Bluetooth signal strength; this is not a GPS or distance measurement.
  5. Wait at least 60 seconds between automatic attempts. A cooldown suppresses repeated screen-on events; it is not a mandatory delay for the main manual button.
  6. Switch the option off in Settings. The background service stops. Demo or key deletion also stops it. OS force-stop requires opening the app again; manufacturer battery controls may restrict it.

For the “off” check, keep the direct-opening widget unused and return to Settings to disable the background option before a screen-on test. A widget-triggered short-lived notification is a separate function and must not be mistaken for the persistent opt-in background service. No fake or simulated foreground-service video is provided.

10. Android widgets only

iOS build 11 contains no widgets, widget extension or widget instructions. The following section applies only to Android build 3.

  1. In Settings choose «Добавить ярлык приложения» to add the launcher. Tapping this widget opens the app only; it intentionally does not send an opening command.
  2. Choose «Добавить виджет открытия» for direct opening. If the launcher does not support the pinning request, use its normal widget list to add an Austria Key widget.
  3. For actual opening, first import operational access, complete the controller association and allow Bluetooth in the main app. Leave Demo off and stand near the assigned controller.
  4. Tap the direct-opening widget. If the phone is locked, complete the system's owner-unlock confirmation. Cancelling authentication does not send a command. The app does not bypass the phone lock.
  5. A short-lived connected-device service sends one authenticated command; the widget/service status reflects progress or error. On older Android versions a temporary execution screen may remain until completion. The operation is distinct from the persistent screen-on service.

Home-screen widgets are the fallback. Placement on the lock screen depends on the Android version and manufacturer's launcher. Neither build claims universal lock-screen placement. In Demo, the direct-opening widget reports that no command was sent; it does not simulate relay success. Missing access, Bluetooth, system association or permissions leads to an explanatory message, not a successful opening.

12. Local operation and data

The mobile app makes no internet requests, reads no GPS coordinates and has no ads, analytics or tracking SDK. Android's app manifest contains no INTERNET, location or Bluetooth scan permission. It uses system association rather than app-level background location. Import recognition and command signing happen locally.

The phone's non-exportable signing key remains in protected device-only storage (Secure Enclave/Keychain on iOS and Android Keystore on Android). The controller authenticates the phone and the app verifies the controller. Signed fresh challenges protect commands against reuse; this guide does not claim payload confidentiality or that a bare Bluetooth connection is sufficient authorization.

The operator registry links assigned access, phone public key, property/gate and issuance/revocation state for authorization. The private phone key does not enter the registry. The controller, not the mobile app, exchanges registry information over its own network. Deleting the app's local key is distinct from revoking access or removing the operator's record; contact the operator for the latter.

Browser downloads, app-link fallback pages, cloud-file providers and store services are separate network actions. The Google Play-distributed Android build has Google Play automatic source-of-install protection enabled; Play services may occasionally need internet for their own checks or offer the official store version after an unofficial installation. This does not give the app an operator-server connection, and it does not authorize physical access. It is not an iOS behavior.

Access service is intended for users aged 9 and older. For minors, access issuance and personal-data requests are handled by the parent/legal representative and operator. The app is not an Apple Kids Category product and has no automated age/parental-consent flow. TestFlight's separate age restrictions are not overridden by the service's minimum age.

Public documents: Privacy policy (Russian), Terms (Russian), User help (Russian). Privacy and terms are also bundled in the apps for offline reading.

13. Evidence and limitations

Apple: the private review attachment austria-key-manual-gate-demonstration.mp4 shows a physical iPhone, ordinary button presses and the compatible controller/isolated relay. It is an earlier recording supplied during build 8 testing, not a physical test of build 11. The ordinary BLE implementation is unchanged; iOS widgets were removed. No simulator or Mac test is presented as physical iPhone verification.

Android: the following owner-supplied recordings show a physical Android device. They are documentation of the recorded scenarios, not evidence that the app was installed through Google Play.

  • Android background-mode demonstration: the screen-on setting is enabled and the persistent service notification is shown. This clip does not document disabling the option or a direct-widget command.
  • Android ordinary-button demonstration: three manual commands receive confirmation. This is not foreground-service or widget proof.

A promotional image on a manufacturer's stock lock-screen wallpaper, if visible in a recording, is device-system wallpaper, not advertising placed by Austria Key. The app itself has no advertising.

Import formats and public QR images have been checked against the production parser. iOS build 11 Simulator regression checks cover ordinary Demo, offline documents, cold/warm import links and native Help without iOS widget instructions, plus protected-storage unit tests. These checks do not validate radio timing, controller actuation or an entire physical-phone background workflow. Android widget support is implemented separately; the ordinary-button and background clips above do not claim to demonstrate it.

Краткое резюме на русском

Инструкция выше полностью описывает версии iOS 1.0.0 (11) и Android 1.0.0 (3) для ревьюера. Само приложение работает локально: импортирует готовый ключ, связывается с калиткой по Bluetooth и не обращается в интернет. Связь с реестром и первая привязка доступа выполняются отдельным контроллером через его Wi-Fi. Пользователь ничего не показывает администратору с телефона.

Для проверки без оборудования включите в настройках «Демонстрационный режим». На iOS кнопка станет «Проверить демонстрацию», на Android останется «Нажмите, чтобы открыть». Итоговое сообщение явно сообщает, что команда не отправлялась. Публичные QR и JSON A/B на этой странице позволяют проверить только импорт: они не зарегистрированы для реального открытия.

Проверяйте образцы в пустом приложении. После импорта верните Demo в положение «включено»: на iOS новый импорт выключает его автоматически. Для следующего способа импорта удаляйте только сохранённый публичный образец, никогда не удаляйте реальный ключ пользователя. Повтор A не заменяет доступ. При B поверх A iOS отказывает, Android запрашивает подтверждение замены; для проверки сохранности выберите «Отмена», затем отдельно удалите только A и импортируйте B.

В iOS 11 виджетов нет. В Android 3 ярлык только открывает приложение, виджет открытия отправляет команду с системной проверкой владельца заблокированного телефона. Фоновый режим включается отдельно: iOS зависит от событий Bluetooth и не гарантирует открытие по включению экрана; Android использует постоянное уведомление и паузу не менее 60 секунд между автоматическими попытками. Подтверждение команды означает ответ контроллера, а не измерение положения калитки.

Настоящая проверка требует выданного рабочего доступа и совместимого контроллера рядом. Рабочие тестовые QR и сведения доступа передаются ревьюеру приватно, не через эту публичную страницу. Поддержка: info@kk-austria.info.

This page has no analytics, third-party fonts or tracking scripts. The public samples are for import testing only; they do not provide operational gate access.
